# Edvora Multi-Tenant SaaS — Database Security Audit Report

> [!IMPORTANT]
> **Audit Classification**: PRE-DEPLOYMENT ARCHITECTURAL & DATABASE SECURITY AUDIT  
> **Target System**: Edvora Tuition Management Platform (Sri Lanka)  
> **Scope**: Migrations `00007`–`00012`, Architectural Documents, Existing Schema (`00001`–`00006`), Storage Policies, and Subscription Security.  
> **Status**: PREPARATION & REVIEW ONLY (Zero SQL executed against production).

---

## 1. Executive Summary

A comprehensive multi-vector security audit was performed across the prepared multi-tenant migrations (`00007` to `00012`), the existing production migrations (`00001` to `00006`), and the accompanying architectural documentation.

The audit revealed **2 Critical**, **3 High**, **2 Medium**, and **1 Low** vulnerabilities in the initial migration drafts:
- **Critical Issues**: (1) Unauthenticated direct CDN bypass of storage policies due to a legacy `public = true` flag on the `notes` bucket, and (2) Admin self-elevation / unauthorized owner appointment due to unconstrained `WITH CHECK` clauses on `tenant_members`.
- **High Issues**: (3) Missing database architecture for commercial paid-only subscriptions and quota limits, (4) Dangerous rollback plan restoring permissive single-teacher RLS across multiple tenants, and (5) Profile role escalation risk via unconstrained update policies.
- **Medium & Low Issues**: (6) Workspace slug mutability impacting URL and email persistence, (7) Absence of a platform administrator entity, and (8) Storage lookup index efficiency.

All identified vulnerabilities have been remediated in the migration files (`00007`–`00012`), and two new sequential migrations (`00013_subscription_and_commercial_billing.sql` and `00014_subscription_enforcement_and_rls.sql`) have been authored to implement the commercial subscription model.

## 3. In-Depth Vulnerability Analysis & Corrections

### SEC-001: Storage Bucket `notes` Marked Public — RLS Bypass on Direct CDN URLs
- **Severity**: **CRITICAL**
- **Location**: `supabase/migrations/00006_notes_feature.sql` (Line 43) and `00012_storage_tenant_policies.sql`.
- **Vulnerability Explanation**:
  In `00006_notes_feature.sql`, bucket `notes` was provisioned with `public = true`. In Supabase Storage, public buckets serve all files directly through the public object endpoint (`/storage/v1/object/public/notes/...`) without evaluating Row Level Security on `storage.objects`. Any client possessing or guessing a document's path could download paid educational material without authentication or tenant authorization, completely undermining tenant isolation.
- **Remediation**:
  Updated `00012_storage_tenant_policies.sql` to explicitly convert bucket `notes` to private:
  ```sql
  UPDATE storage.buckets SET public = false WHERE id = 'notes';
  ```
  All access to notes files now mandates either signed URLs generated by authorized server actions or authenticated Supabase Storage API requests subject to tenant RLS.
- **Status**: **CORRECTED**.

---

### SEC-002: Admin Self-Elevation and Unauthorized Owner Creation in `tenant_members`
- **Severity**: **CRITICAL**
- **Location**: `00007_create_tenant_infrastructure.sql` (Lines 100-136) and `00011_multi_tenant_rls_policies.sql` (Lines 93-110).
- **Vulnerability Explanation**:
  1. `tenant_members_insert_admin` in `00011` allowed any tenant admin to insert rows into `tenant_members` with `WITH CHECK (has_tenant_role(tenant_id, 'admin'))`. It lacked a check restricting `role != 'owner'`.
  2. `tenant_members_update_admin` permitted admins to update member roles, allowing an admin to promote themselves or peers to `owner`.
  3. The safety trigger `check_tenant_member_safety()` only checked that the last owner was not deleted; it did not prevent non-owners from creating new owners or ordinary members from updating their own roles.
- **Remediation**:
  1. Updated `00007_create_tenant_infrastructure.sql` with an expanded `check_tenant_member_safety()` trigger:
     - Disallows inserting `role = 'owner'` unless caller is already an owner or during initial workspace creation.
     - Disallows self-role modifications for non-owners (`OLD.user_id = auth.uid()`).
     - Disallows promoting anyone to `owner` unless performed by an existing owner or via `transfer_tenant_ownership()`.
  2. Updated `00011_multi_tenant_rls_policies.sql` to explicitly segregate owner and admin privileges:
     ```sql
     -- Admins can only insert non-owner roles
     WITH CHECK (
       (role = 'owner' AND public.has_tenant_role(tenant_id, 'owner'))
       OR (role != 'owner' AND public.has_tenant_role(tenant_id, 'admin'))
     );
     ```
- **Status**: **CORRECTED**.

---

### SEC-003: Missing Database Architecture for Paid Subscriptions & Commercial Enforcement
- **Severity**: **HIGH**
- **Location**: `00007_create_tenant_infrastructure.sql` (Lines 16-17).
- **Vulnerability Explanation**:
  The initial architecture featured hardcoded `plan TEXT DEFAULT 'free'` and `max_students INTEGER DEFAULT 25` columns on `public.tenants`. Edvora is a **paid-only commercial SaaS** where starter packages begin at LKR 3,000/month. There was no support for configurable plans, billing cycles (monthly/annual), subscription states (`pending`, `active`, `expired`, `suspended`), manual bank transfer verification, audit history, or server-side quota enforcement.
- **Remediation**:
  Authored two comprehensive new migrations:
  1. `00013_subscription_and_commercial_billing.sql`:
     - `subscription_plans`: Configurable plans with monthly and annual pricing in LKR, max student counts, and storage allocations. Initialized with Starter (LKR 3,000/mo, 30 students, 2GB), Growth (LKR 6,000/mo, 100 students, 10GB), and Pro (LKR 12,000/mo, 300 students, 50GB).
     - `tenant_subscriptions`: Tracks lifecycle states (`pending`, `active`, `expired`, `suspended`), billing periods, and optional admin limit overrides.
     - `subscription_payments`: Tracks manual bank deposit slips, reference numbers, submission proofs, and admin verification logs.
     - `subscription_history`: Comprehensive audit log tracking all status transitions.
     - `platform_admins`: Dedicated entity and `is_platform_admin()` helper.
     - Server-side procedure `admin_verify_subscription_payment()` for atomic verification.
  2. `00014_subscription_enforcement_and_rls.sql`:
     - Trigger `enforce_tenant_student_quota` on `public.enrollments`: Rejects student enrollments exceeding the tenant's plan quota or if subscription is inactive.
     - Trigger `enforce_active_subscription_for_mutations` on `batches`, `lessons`, `notes`, and `announcements`: Rejects content creation when a workspace is expired or suspended.
- **Status**: **CORRECTED**.

### SEC-004: Insecure Rollback Script Restores Permissive Single-Teacher Policies
- **Severity**: **HIGH**
- **Location**: `docs/saas/DATABASE_ROLLBACK_PLAN.md` (Lines 145-212).
- **Vulnerability Explanation**:
  The previous rollback plan dropped multi-tenant RLS policies and re-established legacy single-teacher policies (e.g., `USING (public.is_teacher())`). If executed in an environment where multiple teachers had already signed up, every teacher would immediately gain visibility and control over all other teachers' profiles, batches, lessons, and notes.
- **Remediation**:
  Updated `DATABASE_ROLLBACK_PLAN.md` to:
  1. Add an explicit database guard: Abort immediately if `(SELECT count(*) FROM public.tenants) > 1`.
  2. Establish a safe forward-recovery protocol as the primary remediation strategy.
  3. Ensure that if emergency rollbacks occur, tables are locked down rather than opened globally.
- **Status**: **CORRECTED**.

---

### SEC-005: Student Profile Role Modification Risk via Admin Update Policy
- **Severity**: **HIGH**
- **Location**: `00011_multi_tenant_rls_policies.sql` (Lines 436-455).
- **Vulnerability Explanation**:
  `profiles_update_tenant_admin` allowed a tenant admin to update rows in `public.profiles` for students in their tenant. Without an explicit constraint restricting the columns modified, an admin could mutate `role = 'teacher'`, elevating a student to teacher globally.
- **Remediation**:
  Enforced in `00011_multi_tenant_rls_policies.sql` that both `USING` and `WITH CHECK` clauses require `role = 'student'`, preventing role changes.
- **Status**: **CORRECTED**.

---

### SEC-006: Workspace Slug Mutability Threatens URL & Email Persistence
- **Severity**: **MEDIUM**
- **Location**: `00007_create_tenant_infrastructure.sql` (Line 21).
- **Vulnerability Explanation**:
  If a workspace owner altered `tenants.slug`, client bookmarks, public links, and synthetic auth mappings generated from the slug would become invalid.
- **Remediation**:
  Added trigger `trg_protect_tenant_slug` in `00007_create_tenant_infrastructure.sql` that raises an exception if `OLD.slug != NEW.slug`. Workspace slugs are strictly immutable post-creation.
- **Status**: **CORRECTED**.

---

### SEC-007: Absence of Dedicated Platform Administrator Entity
- **Severity**: **MEDIUM**
- **Location**: `00001`–`00012`.
- **Vulnerability Explanation**:
  Edvora requires platform-level manual verification of bank transfer slips and subscription oversight. The application previously only recognized `teacher` and `student` roles in `profiles.role`.
- **Remediation**:
  Introduced `public.platform_admins` table and security definer function `public.is_platform_admin()` in `00013_subscription_and_commercial_billing.sql`.
- **Status**: **CORRECTED**.

---

### SEC-008: Storage Object Path Regex Performance Under Load
- **Severity**: **LOW**
- **Location**: `00012_storage_tenant_policies.sql`.
- **Vulnerability Explanation**:
  Policies in `storage.objects` call `split_part(name, '/', 1)`. In high-traffic storage operations, unindexed substring parsing could add minor overhead.
- **Remediation**:
  Documented in the performance specification that `storage.objects` has existing indexes on `(bucket_id, name)`. Because `name` begins with `{tenant_id}/`, B-tree index prefix scans remain highly performant.
- **Status**: **DOCUMENTED & MITIGATED**.

## 4. Remaining Risks & Operational Requirements

1. **Client Code Alignment for Private Storage**:
   Because bucket `notes` is now set to private (`public = false`), existing frontend components that reference raw public URLs (`https://.../storage/v1/object/public/notes/...`) must be updated in Phase 3 to request short-lived signed URLs via `supabase.storage.from('notes').createSignedUrl(...)`.
2. **Platform Admin Provisioning**:
   The initial platform administrator profile must be seeded manually into `public.platform_admins` during production deployment.
